SPLK-1002/ Reference/ Time modifiers Splunk Enterprise 10.4

Time and time modifiers (reference)

Time is not a blueprint section on SPLK-1002, and that is precisely why it is worth a file of its own: it is load-bearing under sections 1.0, 2.0 and 3.0, and a question that looks like it is about timechart or transaction is often really about what -1d@d resolves to. topics/00-foundations-refresher.md states the docs-verified core (epoch storage, the four modifiers, the unit alias table, offset before snap, snapping rounds down, picker precedence). This file assumes all of that and goes past it: the fields that carry time, the full snap grammar with resolved examples, the eval time functions with a complete strftime variable table, bin versus timechart span, and real-time semantics.

1. Where time lives on an event#

Field Created Contains Notes
_time Index time, from the event's timestamp UNIX epoch seconds, an absolute instant The field every time range, timechart, bin and sort-by-time operation uses. Rendered in the viewing user's time zone, never stored in one.
_indextime Index time, from the indexer's clock UNIX epoch seconds, the moment the event was written to the index Not shown in the events list and not in the fields sidebar. Retrieve it with eval it=_indextime or filter it with _index_earliest and _index_latest.
date_hour, date_mday, date_minute, date_month, date_second, date_wday, date_year, date_zone Index time, parsed out of the timestamp text The components of the timestamp exactly as it was written in the raw event Present only for events that carried timestamp information generated by the source system.

_time is an integer, so two users in Dublin and Tokyo searching earliest=-24h get the identical event set and see different clock faces. The moment a range references a calendar boundary (@d, @mon, the Today or Since 00:00:00 presets), that equivalence breaks: local midnight is a different epoch instant in each zone, so the two users genuinely get different events. The docs state the storage rule plainly: "Regardless of how time is specified in your events, timestamps are converted to UNIX time and stored in the _time field when your data is indexed."

Why the date_* fields are a trap rather than a convenience:

  • They exist only when the source system put a timestamp in the event. Events whose time Splunk had to infer (file modification time, index time, an upstream default) have no date_* fields at all, so date_hour>=9 silently drops them.
  • They describe the timestamp as written, including whatever zone that timestamp was written in, with date_zone carrying the offset. They do not follow the viewing user's time zone preference the way a rendered _time does. Two events that are simultaneous in absolute terms can carry different date_hour values.
  • date_wday and date_month are lowercase names (wednesday, july), not numbers, so range comparisons on them do not do what an unwary where expects.
  • They are index-time fields, so they are fixed at ingest and cannot be corrected by a search-time knowledge object.

The portable replacement is always to derive from _time:

Search
index=main sourcetype=access_combined_wcookie
| eval hour = strftime(_time, "%H"), wday = strftime(_time, "%A")
| stats count BY hour

_indextime earns its keep for one job: measuring ingest lag, and finding events that arrived long after they happened.

Search
index=main earliest=-7d@d latest=now
| eval lag_seconds = _indextime - _time
| stats avg(lag_seconds) AS avg_lag max(lag_seconds) AS worst_lag BY sourcetype

2. The four time modifiers#

Modifier Filters on Default when omitted
earliest _time The Time Range Picker value, or the beginning of the index if the range is All time
latest _time now(). Specifying only earliest sets latest to the current time.
_index_earliest _indextime None. Nothing is filtered by index time unless you ask.
_index_latest _indextime None.

Rules that decide questions:

  • A time range specified in the search bar, or in a saved search, overrides the range selected in the Time Range Picker. Picker set to Last 7 days plus earliest=-30m in the bar gives you thirty minutes.
  • latest is exclusive at the boundary. With latest=02:00:00, an event stamped exactly 02:00:00 is out. This is what makes earliest=-1d@d latest=@d a clean, non-overlapping "yesterday".
  • Time modifiers do not cross the subsearch boundary in either direction. A subsearch with no modifiers of its own inherits the picker, not the outer search's inline range.
  • earliest=1 latest=now() is an effective all-time search, starting one second after the epoch.
  • The two index-time modifiers are written with a leading underscore. The docs are explicit about the pairing requirement: "When using index-time based modifiers such as _index_earliest and _index_latest, your search must also have an event-time window which will retrieve the events." A search for events indexed in the last hour whose event time is three days old needs a wide earliest as well, or it returns nothing and looks broken.
Search
index=main earliest=-30d@d latest=now _index_earliest=-1h@h _index_latest=@h

Absolute times use the timeformat default %m/%d/%Y:%H:%M:%S, quoted:

Search
index=main earliest="11/15/2022:20:00:00" latest="11/22/2022:20:00:00"

3. Relative time syntax in full#

[+|-]<time_integer><time_unit>@<time_unit>

Everything is optional except that something must be there. -1d, @d, -1d@d and -1d@d+3h are all legal. A missing integer means one: -h is -1h.

Unit Every accepted spelling
Subseconds us (microseconds), ms (milliseconds), cs (centiseconds), ds (deciseconds)
Second s, sec, secs, second, seconds
Minute m, min, mins, minute, minutes
Hour h, hr, hrs, hour, hours
Day d, day, days
Week w, week, weeks
Month mon, month, months
Quarter q, qtr, qtrs, quarter, quarters
Year y, yr, yrs, year, years

Note what is not on that list: M for month and mm for minute do not exist. m is always minutes. Months are always mon or longer.

Snapping, stated as three rules:

  1. Snapping always rounds down, to the latest time that is not after the value being snapped. There is no round-up and no round-to-nearest. Snapping also zeroes every unit smaller than the snap unit.
  2. The offset on the left of @ is applied before the snap on the right. -2h@h is "go back two hours, then drop to the top of that hour".
  3. An offset written after the snap unit is applied last. @d-2h is "start of today, then back two hours" and -1d@d+3h is "yesterday, snap to its start, then forward three hours", which is 03:00 yesterday.

Day-of-week snapping uses @w0 through @w7. w0 and w7 are both Sunday, w1 is Monday and w6 is Saturday. A bare @w (or @week) snaps to the start of the week, which is Sunday, not Monday. A business week that starts on Monday must be written @w1.

Resolved against a concrete now#

Take now as Wednesday 22 July 2026, 14:37:12 in the user's time zone.

Expression Resolves to Comment
now Wed 22 Jul 14:37:12 As a modifier it is bare now; in eval it is now().
@s Wed 22 Jul 14:37:12 Drops subseconds only.
@m Wed 22 Jul 14:37:00
-15m@m Wed 22 Jul 14:22:00
-1h@h Wed 22 Jul 13:00:00 Pair with latest=@h for the last complete hour.
@h Wed 22 Jul 14:00:00 Start of the current, incomplete hour.
-24h Tue 21 Jul 14:37:12 What the Last 24 hours preset means.
-1d Tue 21 Jul 14:37:12 Same instant as -24h except across a DST change.
-1d@d Tue 21 Jul 00:00:00 Start of yesterday, 38 hours 37 minutes ago, not 24.
@d Wed 22 Jul 00:00:00 Start of today.
@d-2h Tue 21 Jul 22:00:00 Snap first, then offset.
-1d@d+3h Tue 21 Jul 03:00:00 Offset, snap, offset.
+1d@d Thu 23 Jul 00:00:00 Forward offsets are legal and useful for latest.
-7d@d Wed 15 Jul 00:00:00
-30d@d Mon 22 Jun 00:00:00
@w / @w0 / @w7 Sun 19 Jul 00:00:00 Week starts Sunday.
@w1 Mon 20 Jul 00:00:00 This week's Monday.
@w6 Sat 18 Jul 00:00:00 The most recent Saturday, which is in the previous week.
-1w@w Sun 12 Jul 00:00:00
-5d@w1 Mon 13 Jul 00:00:00 With latest=@w6 this is the previous business week.
@mon Wed 1 Jul 00:00:00
-1mon@mon Mon 1 Jun 00:00:00 Start of last calendar month.
@q Wed 1 Jul 00:00:00 Q3 2026 begins.
-1q@q Wed 1 Apr 00:00:00

-1y@y Wed 1 Jan 2025 00:00:00
flowchart LR A["-1d@d<br/>Tue 21 Jul 00:00:00<br/>start of yesterday"] --> B["-1d and -24h<br/>Tue 21 Jul 14:37:12<br/>exactly one day back"] B --> C["@d<br/>Wed 22 Jul 00:00:00<br/>start of today"] C --> D["-1h@h<br/>Wed 22 Jul 13:00:00"] D --> E["now<br/>Wed 22 Jul 14:37:12"]

Read that left to right as earlier to later. -1d@d sits to the left of -1d, because the snap moved backwards from Tuesday afternoon to Tuesday midnight. That single ordering fact is the whole of trap T-TM-01.

Preset Equivalent modifiers

Week to date earliest=@w latest=now
Business week to date earliest=@w1 latest=now

Year to date earliest=@y latest=now
All time earliest=1 latest=now

4. Time functions in eval#

Function Returns Behaviour worth knowing
now() Epoch seconds The time the search started, or the scheduled run time for a scheduled search. Constant for every row in the result set.
time() Epoch seconds with microsecond resolution Wall-clock time at the moment each result passes through, so it differs row to row. In a real-time search it is current machine time.
relative_time(<epoch>, <specifier>) Epoch seconds Applies the full section 3 grammar to any epoch value, not just to now. The specifier is a quoted string.
strftime(<epoch>, <format>) String Requires the input in seconds. Millisecond, microsecond or nanosecond values must be divided by 10^3, 10^6 or 10^9 first.
strptime(<string>, <format>) Epoch seconds Needs a day component (a month and year alone will not parse), accepts dates of 1 January 1971 or later, and does nothing at all if pointed at _time, which is already epoch.
Search
| makeresults
| eval start_of_yesterday = relative_time(now(), "-1d@d")
| eval as_text = strftime(start_of_yesterday, "%A %d %B %Y %H:%M:%S")
| eval parsed = strptime("2026-07-22 14:37:12", "%Y-%m-%d %H:%M:%S")
| eval age_days = round((now() - parsed) / 86400, 2)

5. bin, bucket and span#

bucket is an alias for bin. Both are dataset processing commands, so they hold the full result set before emitting.

Search
bin [<bin-options>...] <field> [AS <newfield>]
Option Syntax Default Effect
bins bins=<int> 100 Maximum number of bins. Splunk picks the smallest bin size that produces no more than this many, so you often get fewer.
span span=<log-span> or span=<span-length> none Explicit bin size. Wins over bins.
minspan minspan=<span-length> none Floor on the inferred span.
start / end start=<num> / end=<num> none Numeric range to bin over. Values outside are still returned.
aligntime aligntime=(earliest|latest|<time-specifier>) none Aligns bins to something other than epoch 0. Ignored if span is in days, months or years.

Span forms:

  • Log span: [<num>]log[<num>], coefficient at least 1.0 and less than the base, base greater than 1.0.
  • Span length: <int><timescale>, defaulting to seconds if the timescale is omitted, so span=300 is five minutes.
  • Subsecond spans use us, ms, cs, ds and should divide evenly into a second. The documented valid millisecond values are 1, 2, 4, 5, 8, 10, 20, 25, 40, 50, 100, 125, 200, 250 and 500.
  • A span of a day or more is aligned to midnight.
  • 1mon is a calendar month, not thirty days, and 1q is a calendar quarter. timechart documents sec, min, hr, day, week, month, quarter and subseconds as span-length timescales; years are not on that list. Use span=12mon rather than span=1y.
  • Snap-to spans are restricted on timechart to weeks: span=w@w1 for weeks starting Monday.

bin plus stats versus timechart span#

They are not interchangeable, and the differences are all testable.

Behaviour bin _time span=1h | stats count BY _time, host timechart span=1h count BY host
Output shape Long: one row per bucket per host Wide: one row per bucket, one column per host
Empty buckets Absent. A quiet hour produces no row. Filled. cont=true keeps the series continuous with zeros or nulls.
Partial first and last bucket Whatever the data gives partial=true retains them, and only the first and last can be partial
Search range Only buckets that contain events appear fixedrange=true enforces the search range even where there are no events
Split cardinality Unlimited Capped at the top 10 split values by default, with the rest folded into OTHER
Number of grouping fields Any number One split field only, because _time already occupies the row axis
Field flexibility Any numeric field, not just _time _time only

The practical rule: use bin when you want time as one grouping key among several, or when you need the long shape for a downstream stats, xyseries or eventstats. Use timechart when you want a chartable time series with gap filling.

When span is omitted on timechart#

timechart falls back to bins=100 as a maximum and to a preset-dependent default span. If both bins and span are given, span wins and bins is ignored.

Time range preset Default span
Last 15 minutes 10 seconds
Last 60 minutes 1 minute
Last 4 hours 5 minutes
Last 24 hours 30 minutes
Last 7 days 1 day
Last 30 days 1 day
Previous year 1 month

The consequence is that identical SPL changes granularity when someone moves the picker. Pin the span whenever the number of rows matters, and remember that span and bins must be written before the split-by field or Splunk applies them to the split field instead.

6. Real-time versus historical#

A historical search reads events that are already indexed, over a bounded range, and finishes. A real-time search scans events as they arrive for indexing, looks for index-time fields suggesting a possible match, and periodically evaluates the scanned events against the search criteria within the sliding window you defined. It does not finish; you stop it.

Real-time ranges use the same relative grammar with an rt prefix, rt[+|-]<time_integer><time_unit>@<time_unit>:

Search
index=main sourcetype=access_combined_wcookie status=503 earliest=rt-5m latest=rt
Aspect Windowed real-time All time (real-time)
What it covers A sliding window of the stated width Every event from the start of the search onward, with no window
Event lifetime in the results Events drop out of the results when they age past the window edge Events accumulate and persist
Practical ceiling The window The display uses a circular buffer, so once results pass roughly 1,000 you see approximately the most recent 1,000
Picker labels 30 second window, 1 minute window, 5 minute window, 30 minute window, 1 hour window All time (real-time)

Operational facts that make good distractors: real-time search is turned on by default in Splunk Enterprise, but running or saving one requires the admin, sc_admin or power role, or any role holding the rtsearch capability. Concurrent real-time searches can hurt indexing performance, which is why indexed real-time search exists as a lower-impact variant; it is off by default in Splunk Enterprise. Windowed real-time searches can be backfilled through limits.conf, which runs a historical search first to populate the window and then hands over to the live search, so a dashboard panel is not empty for the first five minutes.

7. Decision rules#

Situation Rule
"The last complete hour" earliest=-1h@h latest=@h, never -1h to now
"Yesterday" earliest=-1d@d latest=@d
"The last 24 hours" earliest=-24h latest=now
"So far this week, business definition" earliest=@w1 latest=now
"Events indexed recently regardless of when they happened" _index_earliest plus a deliberately wide earliest
Hour-of-day analysis eval hour=strftime(_time,"%H"), not date_hour
Need time as one grouping key among several bin _time span=... then stats ... BY _time, other
Need a gap-filled chartable series timechart span=...
Row count must be stable across picker changes Set span explicitly
Comparing two arbitrary epoch values relatively relative_time(), not string arithmetic
A months-ago boundary must be deterministic Always snap: -1mon@mon

8. Traps#

T-TM-01 -1d@d means twenty-four hours ago. Wrong. The offset applies first, giving this time yesterday, then the snap rounds down to the start of that day. At 14:37 on Wednesday it resolves to Tuesday 00:00:00, which is over 38 hours back. Twenty-four hours ago is -24h or bare -1d.

T-TM-02 @w snaps to Monday because the working week starts on Monday. Wrong. The week snap lands on Sunday. @w, @w0 and @w7 are all Sunday, @w1 is Monday and @w6 is Saturday. A business-week range must say @w1 explicitly.

T-TM-03 Snapping rounds to the nearest boundary. Wrong. Snapping always rounds down, to the latest time that is not after the value, and zeroes every smaller unit. -30m@h at 14:50 gives 14:00 and can never give 15:00.

T-TM-04 "Yesterday" is earliest=-1d. Wrong, and this is the picker-versus-modifier trap in its purest form. Yesterday is earliest=-1d@d latest=@d, a fixed calendar day. Last 24 hours is earliest=-24h latest=now, a rolling window. Only the second one moves with the clock.

T-TM-05 -1mon from 31 March gives 31 February, or gives thirty days earlier. Wrong on both counts. mon is a calendar unit, so -1mon from 22 July is 22 June, not 22 June minus a day, and from 31 March there is no 31 February, so the result is clamped into February [verify] (the docs do not state the clamping rule, and month-end arithmetic is the one place the syntax is genuinely ambiguous). The deterministic form is -1mon@mon, which always lands on the first of the previous month at 00:00:00.

T-TM-06 Snapping is absolute, so @d is the same instant for everybody. Wrong. _time is absolute, but the snap is evaluated in the searching user's time zone. @d, @w, @mon and the Today and Since 00:00:00 presets produce different epoch instants for users in different zones and therefore different result sets. earliest=-24h does not have this problem. The docs recommend specifying ranges based on the time zone where the indexer resides.

T-TM-07 m means month. Wrong. m is minutes. Months are mon, month or months. -3m is three minutes ago, and a question that reads earliest=-6m next to answer options about half a year is testing exactly this.

T-TM-08 In -2h@h the snap runs first. Wrong. Left of @ runs before right of @. An offset written after the snap unit runs last, which is why -1d@d+3h (03:00 yesterday) and @d-2h (22:00 the previous night) are different instants and neither equals -1d@d.

T-TM-09 latest is inclusive, and omitting it means "no upper bound". Wrong twice. latest is exclusive at the boundary, so latest=@d stops just before midnight and does not double-count the first event of today. Omitting latest sets it to now(), which excludes nothing in practice but is not the same as unbounded.

T-TM-10 _index_earliest=-1h@h on its own returns everything indexed in the last hour. Wrong. Index-time modifiers filter _indextime but do not widen the event-time window: "your search must also have an event-time window which will retrieve the events". Backfilled data indexed today with an event time of last week needs earliest=-7d as well, otherwise the search returns nothing and looks like a broken index.

T-TM-11 date_hour is the hour of the event in my time zone. Wrong. The date_* fields are parsed from the timestamp as written in the raw event, exist only when the source system supplied timestamp information, and do not follow the viewing user's time zone preference. Events with an inferred timestamp have no date_* fields at all. Use strftime(_time, "%H").

T-TM-12 bin _time span=1h | stats count is just a longer way of writing timechart span=1h count. Wrong. stats emits nothing for empty buckets and produces long-format rows with no split limit; timechart fills gaps, enforces the search range, keeps partial end buckets, produces wide format, and caps split values at the top ten with the remainder in OTHER.

T-TM-13 A timechart with no span always produces the same granularity. Wrong. With span omitted it falls back to a maximum of bins=100 and to a preset-dependent default (10 seconds for Last 15 minutes, 30 minutes for Last 24 hours, 1 day for Last 7 days, 1 month for Previous year), so moving the picker changes the row count without touching the SPL. If both are supplied, span wins and bins is ignored.

T-TM-14 span=1y and span=1d@d are valid on timechart. Wrong. The documented span-length timescales are seconds, minutes, hours, days, weeks, months, quarters and subseconds; years are not listed, so use span=12mon. Snap-to spans are supported only for weeks, as in span=w@w1. Separately, aligntime is ignored when the span is in days, months or years.

T-TM-15 strftime() will format any epoch value, and strptime() will normalise _time. Wrong on both. strftime() requires seconds, so a millisecond field must be divided by 1000 first or you get a date in the year 55000. strptime() on _time does nothing, because _time is already epoch; it also needs a day component in the string and rejects dates before 1 January 1971.

T-TM-16 An all-time real-time search shows every matching event indefinitely. Wrong in practice. Results accumulate rather than ageing out of a window, but the display is a circular buffer holding roughly the most recent 1,000 results. Real-time search also needs the rtsearch capability (held by admin, sc_admin and power), and indexed real-time search, the lower-impact variant, is off by default in Splunk Enterprise.

T-TM-17 now() and time() are the same function. Wrong. now() is fixed for the whole search, set at search start or at the scheduled run time, so every row gets the same value. time() is evaluated per result with microsecond resolution, so it varies row to row. Use now() for anything you intend to compare across rows.
