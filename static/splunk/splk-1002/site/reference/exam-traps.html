SPLK-1002/ Reference/ Trap inventory Splunk Enterprise 10.4

Exam trap inventory (consolidated)

Every trap defined anywhere in this study guide, in one place. 292 traps with stable IDs, collected from the ten blueprint topic files, the foundations refresher, and the four reference files that define traps of their own: precedence, time modifiers, regular expressions, and the CIM catalogue. Nothing here is invented: every ID traces to a ## Traps block in a real file, and the "Where it is taught" column names the file and the heading where the underlying material is explained rather than the trap block itself, because the trap block is the summary and the heading is the argument.

Read this file twice. The first pass is the master table, working top to bottom, covering the whole surface. The second pass is the top twenty plus the final-review list, in the last hour.

How the columns work#

ID is stable across the whole guide. If a cram sheet or a self-check answer says "this is T-05-07", it means the row below.

Blueprint section is the exam section the trap bites in, not necessarily the file it lives in. Traps that come from a reference file rather than a blueprint topic file (T-00-nn foundations, T-KO-nn precedence, T-TM-nn time, T-RX-nn regular expressions, T-CIM-nn CIM catalogue) carry a parenthesised section showing where the exam is most likely to test them.

The wrong belief is written as a candidate would actually be thinking it, in the present tense, without hedging. That is the point. You do not recognise a trap by its correct statement; you recognise it by the shape of the thought you were about to have.

Where it is taught gives the filename and the heading. All topic files are under topics/. knowledge-object-precedence.md, time-modifiers.md, regex-for-splunk.md and cim-data-models.md are under reference/.

The top twenty#

Ranked by expected value on the exam: section weight multiplied by how reliably practitioners get this one wrong. Section 3.0 is 15 percent of the paper and is the single densest source of default-value questions, so it takes five slots. Section 10.0 carries 10 percent with no official course behind it, so anything you know only from ES habit is a risk, and it takes two. Section 1.0 is 5 percent and takes one.

1. T-03-01, the transaction defaults. maxspan and maxpause both default to -1, which means the constraint is deactivated, not "unset with some sensible fallback". Only maxevents has a positive default, 1000. The exam builds this as a four-option question where three options are plausible durations. The reasoning that saves you is that a default duration would silently break every unconstrained transaction in the product, so there cannot be one. A negative value on any of the three deactivates that constraint (T-03-14), and 1000 is not a product ceiling (T-03-19): maxopentxn at 5000 and maxopenevents at 100000 are the real ones, and they evict rather than truncate.

2. T-KO-02, aliases before calculated fields. Field aliasing is stage 5, calculated fields are stage 6, lookups are 7, event types 8, tags 9. Everything downstream can see everything upstream and nothing upstream can see anything downstream. That one sentence generates the whole family: a calculated field can consume an alias but an alias cannot consume a calculated field (T-05-06, T-KO-03); a calculated field cannot read a lookup output (T-05-05, T-KO-04); an event type definition cannot reference a tag (T-KO-05); a tag can be applied to an event type (T-KO-06). The exam asks it in every one of those disguises across sections 4, 5, 6 and 10, so it is worth more than its nominal weight. If you learn nothing else, learn the number of each stage.

3. T-06-01, a tag attaches to a field-value pair. Not to an event, not to a field. You cannot tag "this event". You tag host=web01. The event only carries the tag because it contains that pair. The distractor set almost always contains "a tag is applied to a field" beside "a tag is applied to a field-value pair", and the two look close enough at speed that people take the shorter one. The corollary that makes the fact stick is T-06-14: tagging never changes the value, which is why tagging is the standard fix for a host that was renamed mid-history. Tag both old and new values with one tag and search the tag.

4. T-03-10, transaction produces eventcount, not count. A question shows transaction clientip followed by where count>5 and asks why there are no results. The answer is that count is the stats field and transaction never creates it. This is a good question because it punishes exactly the habit an experienced practitioner has: count is so ubiquitous that you stop reading it. Remember the four fields transaction adds: duration in seconds (T-03-03), eventcount, closed_txn, and _time taken from the earliest member event (T-03-04).

5. T-05-01, an alias adds a name, it does not rename. After FIELDALIAS-x = clientip AS src_ip, both clientip and src_ip work as search terms. The docs are explicit that an alias "does not replace or remove the original field name". The thing that actually removes the old name is the rename command, and that lasts one search and operates downstream of all nine search-time stages (T-05-02). One caveat that catches people who overlearn the additive rule: since 7.2.4, if the source field is missing and the alias field exists, the alias field is removed from the event (T-KO-19).

6. T-08-01, Action type has two values. link and search. Not three. GET and POST are both link actions, separated by link.method. The exam offers "GET, POST, Search" as an answer set constantly because the documentation itself talks about three types of workflow action in prose while the configuration exposes two values for type. Hold both models: three conceptual kinds, two values of type, and the discriminator between the first two is link.method, which defaults to get (T-08-03).

7. T-03-12, first/last against earliest/latest. first() returns the first value in processing order, and because search results arrive newest first, that is usually the most recent event, not the oldest. last() returns the oldest. If you want chronological semantics you must use earliest() and latest(), which read _time. The trap works because the English words point the opposite way from the behaviour. Say it to yourself as "first means first seen, and the first thing you see is the newest".

8. T-04-01, extractions are search-time and retroactive. Saving a field extraction in the Field Extractor writes a search-time configuration. It applies immediately to every event already on disk, needs no reindex and no restart. Candidates who have done real ingest work are the ones who get this wrong, because they associate "new field" with "new parsing". The clean split (T-KO-08): only TRANSFORMS-, line breaking, timestamp assignment, host assignment and source type assignment are index-time and therefore need reindexing. Everything in sections 4, 5 and 6 is search-time and retroactive.

9. T-03-13, values() against list(). values() returns the distinct values, lexicographically ordered, with no documented cap. list() returns every value in event order and stops at 100. The 100 is the examinable number and the one people do not know. When a question describes a scenario with a high-cardinality field and asks why the result set is incomplete, list() is the answer. The parallel inside transaction is mvlist (T-03-07), which defaults to false and gives you the unique-alphabetical rendering, with mvlist=true giving arrival order.

10. T-07-02, the number in the macro name is the argument count. A macro that takes two arguments is stored under the name mymacro(2) and invoked as `mymacro(foo,bar)`. The stored name carries a count; the call carries values. The related fact is that [foobar] and [foobar(1)] are genuinely different objects (T-07-11), so calling `foobar(x)` when only [foobar] exists is an error rather than a call with an ignored argument. And the Arguments form field holds bare names, val, rate, while the Definition references them as $val$ and $rate$ (T-07-03).

11. T-10-03, tags are what admit an event into a CIM dataset. Renaming your fields to src, dest and action does nothing on its own. The event dataset's constraint is a tag expression, so without tag=authentication on the event the Authentication model never sees it. Compliance is tags plus populated required fields, both. The follow-on (T-10-12) is that a child dataset inherits the parent constraint, so the Web model's Proxy dataset needs web and proxy, and tagging only proxy leaves the event out of both.

12. T-09-06, Required is a filter. Marking a field Required on a data model dataset is not documentation and not form validation. It acts as an extra constraint: any event lacking that field is removed from the dataset. Mark a sparse field Required and your dataset silently shrinks. Contrast with Hidden (T-09-07), which only suppresses the field from Pivot users defining a report and changes neither the dataset nor SPL access. Required filters events; Hidden filters what one UI shows you.

13. T-02-03, NOT field=value against field!=value. status!=404 requires the field to exist and to hold something other than 404, so events with no status are dropped. NOT status=404 is set complement over the whole result set, so events with no status survive. The two extreme cases make the rule memorable: NOT field=* returns exactly the events where the field is null or undefined, and field!=* returns nothing at all, ever. Pair this with T-02-02: search evaluates OR before AND, while eval and where evaluate AND before OR, so the same written expression means different things in the two contexts.

14. T-05-07, EVAL- configurations in a stanza run in parallel. Two calculated fields in the same props.conf stanza cannot chain. Write EVAL-response_time = response_time/1000 and then EVAL-bitrate = bytes*1000/response_time and the second still reads the original extracted millisecond value. The reason this is dangerous rather than merely wrong is that it produces a plausible number, not a null and not an error, so nothing in the UI tells you. Lexicographical naming does not fix it (T-KO-14). The only fix is one expression that does both steps, or a second stanza.

15. T-03-05, closed_txn and the endswith omission. closed_txn is set to 1 only when one of maxevents, maxspan, maxpause or startswith is specified. endswith is not on that list, which reads as an inconsistency and is exactly why it is examinable. If none of the four is present, every transaction comes out with closed_txn=0. Keep it distinct from the orphan marker: keepevicted=true surfaces open transactions flagged closed_txn=0, while keeporphans=true surfaces events that joined nothing, flagged _txn_orphan=1 (T-03-06, T-03-20). Both options default to false.

16. T-08-05, the workflow action field list is a conjunction. fields = src_ip, dest_ip means the action appears only on events carrying both. Not either. The documented example spells it out: *, ip_client, ip_server applies to all fields in the event if ip_client and ip_server are both present. The companion default is that fields defaults to * (T-08-04), so an action you never scoped appears everywhere, and display_location defaults to both (T-08-12), so it appears in the event menu and every field menu.

17. T-10-02, CIM acceleration is off by default. Every data model in the CIM add-on ships with acceleration disabled. You turn it on per model on the CIM Setup page. The consequence the exam likes is that a tstats summariesonly=t search against a freshly installed CIM model returns zero rows, which reads like a broken search and is actually correct behaviour. The Apress answer key asserts the opposite, so if you revised from that book you have this backwards. Also on the setup page: the Indexes allowlist defaults to all indexes (T-10-04), not to empty.

18. T-06-05, priority 1 beats priority 10. Event type priority is an integer 1 through 10 and 1 is best. The docs' own example gives critical_disk_error priority 3 and all_system_errors priority 7, and describes 3 as the better value. Priority does two jobs, not one (T-06-06): it orders matching event types in the display, and it decides which single colour renders when several matching event types define one. Event types with no priority set sort alphabetically below all those that have one.

19. T-09-11, summariesonly defaults to false. By default tstats runs over accelerated and unaccelerated data models alike, so it works whether or not you turned acceleration on. Setting summariesonly=true restricts the search to summarized data, which is faster and is incomplete for any time outside the Summary Range. The frequent misreading is that tstats is a summaries-only command by nature. It is not. Sitting beside it: strict_fields on the datamodel command defaults to true (T-09-12), which is why datamodel M D search shows you fewer fields than the dataset defines.

20. T-01-01, limit caps columns. On chart, limit defaults to top 10, is only valid when a column-split is specified, and limits the number of columns. On timechart, limit defaults to top10 distinct split-by values, and the number of rows comes from span or bins. Nothing about limit on either command constrains rows. limit=0 means all, not none (T-01-17). And on top and rare, limit genuinely does control the number of rows returned, which is the source of the confusion.

Just below the line, and worth a glance if you have time: T-03-09 (stats outperforms transaction, which is centralized streaming and search-head only), T-08-02 (link.target defaults to blank, a new window), T-02-02 (Boolean precedence differs between search and where), T-04-09 (max_match defaults to 1 and max_match=0 means unlimited), T-07-01 (backticks, not quotation marks), T-09-01 (the data model feeds Pivot, not the reverse).

Macro name argument count vs invocation arguments The stored name carries the count, mymacro(2); the invocation carries the values, `mymacro(foo,bar)`. [foobar] and [foobar(1)] are different objects.
maxspan vs maxpause vs maxevents maxspan is total transaction duration; maxpause is the longest gap between adjacent events; maxevents is the member count. First two default to -1 (off), the third to 1000.
mvindex() vs substr() index base mvindex() and mvfind() count from 0 with -1 as the last element; substr() counts from 1 with SQLite semantics.
Name vs Label (workflow action) Name is the internal object name and becomes the stanza header; Label is the menu text and is the field that accepts $field$ tokens.
NOT vs != NOT field=value keeps events with no field at all; field!=value requires the field to exist.
null() vs nullif() vs isnull() null() takes no arguments and returns NULL; nullif(a,b) returns NULL when the two are equal, otherwise a; isnull(x) returns a Boolean and therefore cannot be assigned directly under eval.
OUTPUT vs OUTPUTNEW (and AS vs ASNEW) OUTPUT overwrites an existing field of that name; OUTPUTNEW writes only when the field is new to the event. ASNEW is the alias equivalent.
OVER vs BY on chart OVER names the row-split, which becomes the first column and the X-axis; BY names the column-split, which becomes the series. chart X BY a b equals chart X OVER a BY b.
Priority vs lexicographic order (event types) Priority orders first and 1 is best; lexicographic order breaks ties and orders every event type that has no priority, below those that do.
Required vs Optional vs Hidden (data model fields) Required filters out events lacking the field; Optional includes the field when present; Hidden only stops Pivot users seeing it while defining a report.
Required vs recommended CIM fields Required fields must be populated for the dataset to work and are the basis of compliance; recommended fields improve coverage for Enterprise Security content but their absence does not exclude the event.
scanCount vs eventCount scanCount is events read off disk; eventCount is the subset that matched the search terms.
search vs where search compares a field to a literal, is case-insensitive on values, and accepts *; where compares field to field, is case-sensitive, has no *, and needs like() with % for prefix matching.
Search-time precedence vs configuration file precedence Search-time precedence is the order in which nine kinds of object are applied to events; configuration file precedence is which copy of a duplicated setting wins the merge across default, app and user directories. Unrelated mechanisms.
Smart vs Fast vs Verbose Smart is the default and discovers all fields only for non-transforming searches; Fast discovers only what the search needs; Verbose discovers everything and disqualifies a report from report acceleration.
Source type rename vs field alias Renaming a source type in props.conf is search-time, moves the original to _sourcetype, and makes the original stanza's extractions stop applying; a field alias adds a name to a field and touches nothing else.
span vs bins span sets the bucket size directly; bins sets a maximum bucket count and Splunk picks the smallest span producing no more than that. If both are given, span wins and bins is ignored.
stats vs eventstats vs streamstats stats replaces events with a results table; eventstats adds the aggregate back onto every event; streamstats adds a running aggregate computed over events seen so far.
summariesonly vs strict_fields summariesonly is on tstats, defaults to false, and restricts results to summarized data; strict_fields is on datamodel, defaults to true, and restricts the field list to defaults plus constraint fields.
Tag vs event type A tag is a label on a field-value pair with no search behind it; an event type is a saved simple search whose matches receive an eventtype field value. Tags run at stage 9, event types at stage 8, so you can tag an event type but not the reverse.
Transaction vs stats transaction builds a single grouped event with _raw, duration and eventcount, is centralized streaming and search-head only, and is bounded by maxevents; stats is transforming, distributes across indexers, and is the documented preference wherever it will do the job.
tstats FROM datamodel= vs from datamodel: tstats uses FROM datamodel=<model>.<root_dataset> with an equals sign; from uses from datamodel:<model>.<dataset> with a colon.
usenull/nullstr vs useother/otherstr usenull covers events missing the split-by field and labels them NULL; useother covers values that lost the limit or where-clause cut and labels them OTHER. Both true on chart and timechart, useother false on top.
values() vs list() values() is distinct and lexicographically ordered with no cap; list() is every value in event order, capped at 100.
Workflow action vs alert action A workflow action fires on a human click in a Splunk Web menu and changes nothing about the data; an alert action fires automatically when a saved search's trigger condition is met.

The last hour: fifteen facts#

Read these in two minutes. Nothing here needs a sentence of context.

  1. Search-time order, nine stages: field filters, EXTRACT-, REPORT-, KV_MODE, field alias (5), calculated field (6), lookup (7), event type (8), tag (9). Downstream sees upstream. Never the reverse.
  2. transaction: maxspan -1, maxpause -1, maxevents 1000. Negative deactivates. Fields added are duration (seconds), eventcount, closed_txn. _time is the earliest member event.
  3. closed_txn=1 requires maxevents, maxspan, maxpause or startswith. endswith does not count. Orphans are _txn_orphan=1; evicted are closed_txn=0. Both options default false.
  4. A tag attaches to a field-value pair. Search syntax tag::<field>=<name> with two colons, or bare tag=<name>.
  5. Event type priority: 1 best, 10 worst. Definition may not contain a pipe, a subsearch, savedsearch, or a tag reference.
  6. A field alias adds a name and keeps the original. rename replaces the name for one search only. Alias scope is host, source, or source type. Nothing else.
  7. All EVAL- in one props.conf stanza run in parallel, never chained. A calculated field overrides an extracted field of the same name even when it evaluates to null. Guard with coalesce.
  8. Macros use backticks. A two-argument macro is stored as mymacro(2). Arguments field holds bare names, Definition holds $name$. Macro expansion happens before stage 1 and is not in the nine.
  9. Workflow action type is link or search only. link.method default get, link.target default blank, display_location default both, fields default * and the list is a conjunction. search.preserve_timerange is ignored if search.earliest or search.latest is set.
  10. CIM: acceleration disabled by default on every model, add-on installs on search heads only, each model searches all indexes by default, and tags are what admit an event into a dataset.
  11. Data models: only root datasets add auto-extracted fields. Required filters events out. Hidden only hides from Pivot. Dataset ID cannot be changed after save. Child constraints cannot contain macros.
  12. tstats summariesonly defaults to false. datamodel strict_fields defaults to true. FROM datamodel=M.D for tstats, from datamodel:M.D for from.
  13. chart limit default top 10 and it caps columns; timechart limit default top10 and takes one BY field. chart bins=300, timechart bins=100. span beats bins. useother is false on top, true on chart and timechart.
  14. NOT field=value keeps events with no field; field!=value drops them. search evaluates OR before AND; eval and where evaluate AND before OR. where has no *; use like() with %.
  15. fillnull default value 0, no wildcards. filldown accepts wildcards and copies the last non-null value. Subsearch defaults: 10,000 results, 60 seconds, silent truncation. rex max_match default 1, and 0 means unlimited.
